# 《AI客来：街角咖啡屋》项目进展总结与后续计划

更新时间：2026-05-10

## 1. 项目定位

《AI客来：街角咖啡屋》是一款面向大学生 AI 主题比赛的轻量化对话式模拟经营游戏。

根据策划案，玩家扮演街角咖啡屋店长，通过“进货、定价、自由文本对话、顾客购买决策、打烊结算、成长解锁”的单日经营循环，逐步提升店铺盈利能力、声望和星级，最终从一星社区小店成长为五星网红咖啡屋。

项目原始核心卖点是：

- AI 顾客不是固定选项，而是能根据性格、上下文和玩家话术进行动态回应。
- 经营策略和对话表达共同影响顾客购买欲望。
- 顾客性格应有明显差异，不同玩家话术会产生不同经营结果。
- 游戏应轻量、易演示、可在比赛现场稳定跑通。

当前项目已经完成“可演示经营闭环 + 本地规则 AI 顾客差异”的基础版本，但真实 AI API 接入效果仍未达到策划案预期，这是目前最需要继续解决的问题。

## 2. 当前项目阶段

项目当前处于：

```text
最小可玩闭环完成
+ 经营数值初步完善
+ 顾客性格差异初步完成
+ UI 可用性持续修正
+ 长期玩法基础框架已加入
+ 真实 AI 接入仍在问题归纳与重构阶段
```

当前版本已经可以跑通基础流程：

```text
进货 / 定价
-> 开始营业
-> 顾客进店
-> 玩家输入文字对话
-> 顾客购买欲望变化
-> 顾客购买或离店
-> 日终结算
-> 进入下一天
```

目前最重要的项目判断是：

```text
核心经营结果必须先由本地规则保证稳定。
真实 AI 暂时不应直接决定库存、成交、结算等关键结果。
真实 AI 下一阶段应定位为“顾客对话表现增强层”。
```

这样可以避免 API 不在本机、网络不稳定、模型输出格式异常、模型回复不符合性格等问题直接破坏游戏闭环。

## 3. 已完成内容

### 3.1 项目结构

当前项目结构已经基本清晰：

- `assets/scenes`：主场景。
- `assets/scripts/core`：核心流程、资金、库存、声望、星级、结算。
- `assets/scripts/data`：商品、顾客、技能、成就数据。
- `assets/scripts/ai`：本地规则 AI、真实 AI 请求、Prompt 构建。
- `assets/scripts/ui`：准备、聊天、结算、新手提示、成长界面。
- `assets/prefabs`：商品项、聊天气泡等预制体。
- `server`：Node.js AI 后端服务。
- `docs`：开发说明、测试用例、项目总结。

### 3.2 核心经营闭环

已完成：

- 玩家初始资金。
- 商品进货。
- 商品定价。
- 库存显示。
- 开始营业。
- 每日顾客生成。
- 顾客依次进店。
- 玩家通过自由文本与顾客对话。
- 顾客购买欲望变化。
- 顾客购买或离店。
- 顾客购买后增加营收、扣除库存。
- 所有顾客结束后进入结算。
- 点击下一天回到准备阶段。

当前库存规则：

```text
进货 -> 库存增加
顾客购买 -> 库存减少
打烊结算 -> 未售库存保留
下一天 -> 继续显示剩余库存
```

说明：策划案中有“鲜制产品打烊报废”的设定，但当前版本暂时没有启用报废清空库存。之前出现过“第二天库存异常清零”的体验问题，因此当前阶段先保留库存，保证玩家能清楚理解“只有卖出才扣库存”。后续如果恢复报废机制，必须在结算界面明确显示报废商品和数量。

### 3.3 商品与定价

已完成：

- 商品数据包含成本、建议售价、标签。
- 进货阶段显示商品名、成本、建议售价、库存。
- 玩家可以输入售价。
- 已增加商品定价功能。
- 点击开始营业前会自动保存当前输入的售价。
- 营业阶段会显示库存和当前售价。
- 售价会影响顾客购买欲望：
  - 售价过高：降低购买欲望。
  - 售价合理：提高购买欲望。

当前商品标签用于匹配顾客偏好，例如：

- 美式：`coffee`、`fast`、`bitter`
- 拿铁：`coffee`、`mild`、`popular`
- 手冲：`coffee`、`premium`、`story`
- 甜点：`dessert`、`relax`、`art`
- 三明治 / 牛角包：`food`、`fast`、`takeaway`
- 热可可：`sweet`、`mild`、`comfort`

### 3.4 顾客性格差异

已完成第三阶段的基础版本。

6 类基础顾客已经具备独立配置：

- 喜欢关键词。
- 讨厌关键词。
- 偏好商品标签。
- 价格敏感度。
- 耐心轮数。
- 决策风格。

当前 6 类顾客差异：

- 社恐内向型：谨慎、短句、怕被强推。
- 挑剔达人型：重视专业、细节、口感描述。
- 文艺青年型：喜欢氛围、故事、情绪价值。
- 社牛自来熟型：喜欢互动、闲聊、熟客感。
- 赶时间上班族：重视效率，耐心更低，决策更快。
- 纠结选择困难型：需要明确推荐和缩小选择范围。

当前购买欲望计算由本地规则负责：

```text
话术匹配分
+ 商品偏好分
+ 价格接受分
+ 性格特殊规则
= 本轮购买欲望变化
```

顾客购买时会：

- 只从有库存商品中选择。
- 优先选择符合自身偏好标签的商品。
- 在候选商品中随机购买，而不是固定买第一个商品。
- 如果没有可购买库存，则离店。

### 3.5 聊天与顾客结果

- 玩家可自由输入文本。
- 支持 Enter 发送。
- 聊天记录可滚动。
- 聊天气泡能根据文本长度调整。
- 顾客购买欲望用进度条展示。
- 顾客最多会在耐心轮数内购买或离店。

  - `结果：购买了 XX`
  - `结果：未购买`

- 全部顾客结束后进入结算。
- 结算后禁止继续给上一位顾客发消息。

## 4. 真实 AI 问题归纳

这是当前项目最重要、且仍未完全解决的问题。

### 4.1 当前真实 AI 没有达到策划案预期

策划案要求：

```text
所有顾客由大模型动态驱动。
顾客拥有独立性格、对话逻辑和决策规则。
玩家自由文本会实时影响购买欲望。
模型输出需要稳定、可解析、符合顾客性格。
```

当前项目虽然已经有本地规则 AI 和后端接口雏形，但真实 API 的效果仍不稳定，主要表现为：

- API 调用生成的顾客回复不够符合预设性格。
- 回复有时像通用客服或普通聊天助手，而不像咖啡店顾客。
- 模型输出格式仍可能不稳定。
- 模型返回内容和本地经营规则之间边界不够清楚。
- API 不在当前电脑时，`localhost` 地址无法访问后端。
- 网络、端口、防火墙、后端启动状态都会影响演示。
- 真实 AI 成功还是回退本地 AI，对玩家和开发者还不够直观。

### 4.2 API 不在本机的问题

如果后端服务不在当前电脑，则不能使用：

```text
http://localhost:3000/api/chat
```

因为 `localhost` 只代表当前运行 Cocos 的电脑。

正确做法应该是：

```text
http://后端电脑IP:3000/api/chat
```

同时后端电脑需要：

- 与当前电脑在同一网络。
- 服务监听 `0.0.0.0`，不能只监听本机。
- 防火墙放行 3000 端口。
- 浏览器访问 `http://后端电脑IP:3000/health` 能成功。

如果比赛或课堂演示现场无法保证后端可访问，建议临时关闭真实 AI，使用本地规则 AI 演示核心玩法。

### 4.3 真实 AI 和本地规则的职责需要重构

当前更合理的架构应该是：

```text
Cocos 本地规则：
负责购买欲望、库存、价格、购买/离店、商品选择、结算。

真实 AI：
只负责把顾客当前状态包装成更自然、更符合性格的回复文本。
```

也就是说，真实 AI 暂时不应该直接决定：

- 是否购买。
- 买什么商品。
- 扣多少库存。
- 增加多少营收。
- 结算结果。

这些必须由本地规则控制，才能保证游戏稳定。

### 4.4 建议的真实 AI 返回格式

下一阶段建议把真实 AI 返回格式简化为：

```json
{
  "message": "顾客回复文本",
  "emotion": "positive | neutral | negative"
}
```

不建议继续让真实 AI 直接返回复杂字段：

```json
{
  "desireDelta": 12,
  "decision": "buy",
  "productId": "latte"
}
```

购买欲望变化、购买决策和商品选择应先由本地规则算好，再传给 AI 作为上下文，让 AI 只负责“怎么说”。

### 4.5 需要增加 AI 调试反馈

后续必须加入更清楚的调试信息：

- 当前使用的是本地 AI 还是真实 AI。
- 真实 AI 是否请求成功。
- 真实 AI 是否超时。
- 真实 AI 返回是否通过格式校验。
- 如果回退本地 AI，回退原因是什么。
- 后端是否收到 Cocos 请求。
- 当前 Cocos 的 `Api Url` 实际请求地址是什么。

这能避免“看起来像本地模板，但不知道真实 AI 有没有生效”的问题。

## 5. 当前存在的问题

### 问题 1：真实 AI 仍未解决

这是最高优先级问题。

当前本地规则 AI 能跑通核心玩法，但真实 AI 还没有稳定达到策划案中的核心竞争力要求。

下一步需要重点解决：

- API 地址配置。
- 后端可访问性。
- Prompt 稳定性。
- 输出格式校验。
- 顾客性格表现。
- 本地规则和真实 AI 的职责边界。

### 问题 2：AI 顾客动态表现还不够强

虽然 6 类顾客已有性格差异，但目前主要依赖本地关键词和模板。

与策划案相比，目前还缺少：

- 更自然的多轮上下文记忆。
- 更强的临场感。
- 更少重复的回复。
- 更明显的个体差异。
- 更像真实顾客的开场白和追问。

### 问题 3：内容安全机制尚未完成

策划案中提到需要内容安全过滤。

当前项目还没有完整实现：

- 玩家输入内容审核。
- 违规内容拦截。
- AI 输出内容校验。
- 不合规回复重试或替换。

如果作为 AI 主题比赛项目，这部分后续需要补上，至少要有基础关键词过滤和兜底提示。

### 问题 4：UI 仍偏原型

当前 UI 已能使用，但还不是策划案中的“2D 卡通咖啡屋全景 + 顾客形象 + 清晰数据面板”的表现。

仍存在风险：

- 个别动态按钮或成长面板在 Cocos 预览中可能需要重新加载场景后才显示。
- 商品列表和聊天区域在不同分辨率下仍需继续检查。
- 缺少顾客头像、咖啡屋背景、商品图标。
- 结算日报仍偏文字化，缺少更直观的数据面板。

### 问题 5：成长系统还不够完整

当前已经有技能、成就、星级和解锁框架，但还不够完整。

需要继续完善：

- 技能升级界面的稳定显示。
- 技能效果的可感知反馈。
- 成就弹窗。
- 商品解锁提示。
- 顾客类型解锁提示。
- 星级提升动画或提示。
- 每周目标完成奖励。

### 问题 6：策划案中的报废机制暂时未启用

策划案要求部分鲜制品打烊后报废，以强化进货策略。

当前版本为了避免玩家误解“库存为什么第二天清零”，暂时选择保留库存。

后续如果恢复报废机制，需要做到：

- 区分“可跨天库存”和“鲜制品库存”。
- 结算日报明确显示报废商品、数量和损失。
- 新手期降低报废惩罚。
- UI 明确标注哪些商品会报废。

### 问题 7：存档与重开机制尚未完善

当前更偏演示原型，还缺少完整存档。

后续需要考虑：

- 本地存档。
- 新游戏 / 继续游戏。
- 设置页。
- 重置进度。
- 演示用调试开关。

## 6. 后续发展计划

### 阶段 A：稳定当前可演示版本

目标：不依赖真实 AI，也能稳定演示 3 天经营。

要做：

- 检查进货、定价、库存、资金变化是否稳定。
- 检查点击开始营业后是否进入 `Business`。
- 检查顾客是否正常出现。
- 检查发送消息后购买欲望是否变化。
- 检查顾客是否在耐心轮数内购买或离店。
- 检查顾客购买结果是否只显示一次。
- 检查顾客购买商品是否从库存中随机选择。
- 检查所有顾客结束后是否进入结算。
- 检查结算后是否不能继续给上一位顾客发消息。
- 检查点击下一天后是否回到准备阶段。
- 检查库存是否正确跨天保留。
- 检查定价是否在营业阶段生效。

### 阶段 B：重构真实 AI 接入

目标：解决当前 AI 问题，让 AI 符合策划案的核心竞争力，同时不破坏经营闭环。

建议方案：

1. 本地规则先算出本轮结果：
   - 欲望变化。
   - 当前购买欲望。
   - 是否购买。
   - 购买商品。
   - 是否离店。

2. 把这些结果传给真实 AI：
   - 顾客性格。
   - 当前商品库存和售价。
   - 玩家话术。
   - 本地规则判定结果。
   - 希望 AI 表达的情绪方向。

3. 真实 AI 只返回：
   - 一句顾客回复。
   - 简单情绪标签。

4. Cocos 校验返回：
   - 如果格式正确，显示真实 AI 回复。
   - 如果格式错误、超时或请求失败，显示本地模板回复。

这样既能保留 AI 对话表现，又不会让模型错误影响库存和结算。

### 阶段 C：优化 Prompt 和顾客表现

目标：让 6 类顾客真的“说话不一样”。

要做：

- 为每类顾客写独立 System Prompt。
- 每类顾客准备 3-5 条示例回复。
- 限制回复长度，适合聊天框显示。
- 要求顾客语气贴合性格，不要像客服。
- 要求顾客回复必须围绕咖啡店、商品、价格、口感和服务体验。
- 加入上下文摘要，减少前后矛盾。
- 对真实 AI 回复做长度限制和内容过滤。

### 阶段 D：补充内容安全

目标：满足 AI 主题比赛的合规要求。

要做：

- 玩家输入基础过滤。
- 明显违规内容拦截。
- AI 输出校验。
- 不合规内容替换成本地安全回复。
- 在项目说明中写清楚安全策略。

### 阶段 E：完善 UI 与美术表现

目标：让项目更像完整游戏，而不是调试工具。

要做：

- 增加咖啡屋背景。
- 增加顾客头像或立绘占位。
- 增加商品图标。
- 结算日报改成更清晰的数据面板。
- 成长面板稳定显示技能树和成就。
- 增加星级、声望、技能点的明显反馈。
- 检查所有界面文字是否越界、重叠或被遮挡。

### 阶段 F：完善长期玩法

目标：对齐策划案中的“成长解锁”。

要做：

- 商品解锁。
- 技能升级实际影响经营。
- 成就弹窗。
- 星级提升。
- 每周目标。
- 更多顾客类型。
- 复购顾客或熟客系统。
- 网红打卡事件。
- 高星级限定商品。

### 阶段 G：测试与交付

目标：准备课堂 / 比赛演示版本。

建议测试清单：

1. 第一天买入商品后资金减少、库存增加。
2. 修改售价后，营业阶段显示正确售价。
3. 开始营业后进入 `Business` 阶段。
4. 顾客正常出现。
5. Enter 可以发送消息。
6. 聊天记录可以滚动。
7. 购买欲望会根据话术变化。
8. 售价过高会降低购买欲望。
9. 售价合理会增加购买欲望。
10. 顾客会在耐心轮数内购买或离店。
11. 顾客购买商品来自库存，且有随机性。
12. 顾客购买后库存减少。
13. 顾客离开后切换下一位。
14. 全部顾客结束后进入结算。
15. 结算界面不和按钮重叠。
16. 下一天后库存保留。
17. 结算后不能继续给上一位顾客发消息。
18. 技能树和成就能在准备阶段看到。
19. 真实 AI 关闭时，本地规则 AI 能完整跑通。
20. 真实 AI 开启但请求失败时，能回退本地 AI。

## 7. 当前建议的演示策略

在 AI API 问题彻底解决前，建议演示时采用“双层表达”：

```text
第一层：本地规则 AI
保证经营闭环、欲望变化、购买决策、库存和结算稳定。

第二层：真实 AI 接入计划
展示项目已经预留后端接口和 PromptBuilder，下一阶段将真实 AI 降级为对话表现增强层。
```

这样既不会回避 AI 问题，也不会让未稳定的 API 拖垮当前演示。

如果现场后端不可用，建议设置：

```text
GameRoot -> AIManager
Use Real AI: 不勾选
```

如果需要联调真实后端，建议设置：

```text
GameRoot -> AIManager
Use Real AI: 勾选
Api Url: http://后端电脑IP:3000/api/chat
Ai Timeout Ms: 8000
Log Real AI: 勾选
```

同时先检查：

```text
http://后端电脑IP:3000/health
```

能否在当前电脑浏览器中打开。

## 8. 总结

当前项目已经具备可演示的核心玩法：玩家可以进货、定价、接待不同性格顾客，通过自由文本对话影响购买欲望，顾客会根据性格、价格、库存和话术决定购买或离店，最终形成每日结算和跨天经营。

但从策划案角度看，项目真正的核心竞争力是“AI 顾客动态对话”。目前真实 AI API 仍未稳定解决，模型回复质量、接口访问地址、输出格式校验、本地规则边界都还需要继续处理。

因此下一阶段的最高优先级不是继续堆更多功能，而是：

```text
先保证本地规则版本稳定可演示；
再把真实 AI 改造成稳定的对话表现增强层；
最后补齐内容安全、UI 美术和长期成长系统。
```

这样项目会更符合策划案，也更适合比赛现场演示。
